# Project rules

These are hard requirements from the project owner.

- Prioritize readable logic over brevity. Use standard if/else blocks instead of complex one-liners.
- Use descriptive names for variables, functions, types, files, and modules.
- Write for a human developer taking over tomorrow. Keep functions small and separate concerns strictly.
- Comments explain why a decision exists, rather than restating what the code does.
- Keep `docs/ARCHITECTURE.md` updated as the project develops. Explain how the app works, how files and functions connect, and how it is built.
- Update documentation alongside changes to responsibilities, call flows, permissions, protocol, dependencies, build steps, and behavior. Document important entry points and public interfaces; avoid an autogenerated inventory of trivial helpers.
- Distinguish proposals, implemented behavior, and physically verified behavior.

Current scope: application development authorized by the owner on 2026-11-02. Begin with native foundations and debugging-free screen performance feasibility. Do not describe unimplemented or untested integration as working.
